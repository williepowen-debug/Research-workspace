## 3. Exact proposed boundary

The receipt carries three explicit path sets, stored in the existing per-run receipt area. This is a per-package manifest, not a maintained fleet register. All paths are repository-relative, normalized and exact; no folder wildcard can establish reviewed scope.

| Set | Includes | Identity and limits |
|---|---|---|
| **Candidate deliverables** | Every authored artifact intended for this package: own reports, STATUS/HANDOFF edits, scripts/specs if authorized, authored packets in recipient inboxes, and any specifically authorized authored memory/shared-path artifact | Path, operation(add/modify/delete), Git mode/type, expected presence/absence, content hash and byte count. Renames represented as old deletion + new addition. Record before-image for changed tracked files and final content. A packet's location is not proof of authorship/authority; retain an explicit declaration and relevant grant. No filename-based blanket authority. |
| **Checked dependencies** | Inputs actually needed for the claims/checks being reused: relevant canonical instructions, invoked checker/runner source and local imports/configuration, declared input inventories, and specific Git-derived inputs where a check relies on them | Each check names its input perimeter and identity basis. Freeze directory membership when additions can change that check's result. A pinned historical source remains pinned; a claim about current state needs current inputs. An input that cannot be enumerated/read is UNKNOWN for that claim, never silently omitted or replaced with a whole-repo hash. |
| **Bookkeeping exclusions** | Initially only the exact `AGENTS/DAEDALUS/runs/GATE_LOG.tsv` path and the specific generated receipt/per-step-log paths for this run | Excluded from substantive identity to avoid self-reference, not exempt from delivery truth or allowed to contain substantive edits. Keep generated records in scratch where possible. A persisted copy is declared by exact path; any other exception needs a specific reason before freeze. Never exclude all runs/, STATUS, HANDOFF, reports, inboxes, source code or evidence merely because of filename. |

A required independent-review report is evidence, not an arbitrary bookkeeping exception. Its hash is bound after the reviewer returns; its contents identify the exact candidate/dependency hashes examined and any unreviewed residue. A later delivery-only receipt may record commit/origin/acknowledgment facts without expanding that reviewed set. If it adds findings or changes a disposition, it becomes substantive candidate content and requires the applicable review. This prevents an exclusion from becoming an unreviewed content channel.

**POST-REVIEW R3 — non-file dependencies:** Bind result-affecting invocation arguments/declarations, working directory, effective calendar day/timezone, specific Git-query results and relevant non-secret configuration/environment context to each check that uses them. C9 uses `date.today()` via `ctx["today"]`; unchanged bytes across midnight do not prove its earlier “today” result remains current. Preserve historical results at their original time; present-state reuse must compare the relevant context. Record only used context at the required granularity, never secrets or the whole environment. Unsupported context is a bounded limitation/UNKNOWN, not a continuous recheck mandate.

Candidate inventory reconciliation precedes freeze: compare explicit authored paths with current own-directory changed/untracked inventory and declared external authored paths; classify each relevant path as included, separate work or foreign, with a reason for exclusions. This is an omission aid, not a proof of authorship. Unknown ownership prevents inclusion under another owner's authority. External writes created later require declaration and recapture. The actual-commit path check below catches undeclared additions even if the inventory missed them. No tool can prove an author declared every intended but undelivered artifact; the completion record must retain that judgment limit.

For ordinary files, identity uses raw bytes. For symlinks, record the link's Git type and target rather than silently hashing an out-of-repository target; if a check follows the link, its resolved input must be a separately declared dependency or UNKNOWN. Git filters/line-ending conversion must not be assumed absent: compare the reviewed working bytes with the eventual stored blob and reject unexplained conversion. A deletion has an explicit tombstone expectation, not an unreadable-file fallback. An actually missing required dependency is UNKNOWN. Unsupported path/type/conversion cases cannot receive a successful boundary certificate.

## 4. Proposed sequence and concurrency behavior

1. **Finish substantive write-back and declare scope.** Write the substantive STATUS/HANDOFF completion entry (coverage, remainder, required review disposition and next action) before freeze; delivery may still be pending. Record candidate paths, required dependencies, relevant obligations, required review or the canonical exemption, and the narrowly named bookkeeping exclusions. Existing root authorship/path/idle rules still control what may be written or committed.
2. **Capture before checks.** Record exact candidate/dependency content and membership. Record HEAD as provenance, not as an undifferentiated assurance invalidator. Record any specific history/ancestry input on which a check actually depends.
3. **Run the applicable existing checks.** Retain each step's native rc, class, applicability declaration and coverage. Capture the same content/membership afterward. If either capture fails, identity is UNKNOWN; if substantive bytes/membership differ, the check results cannot certify the final candidate. Merely hashing at the end is prohibited because it would bless unchecked intervening edits. End-point comparison detects persistent changes, not a transient change-and-revert; checks requiring a stronger stability guarantee need pinned inputs or an explicit unverified limitation before an implementation can claim that guarantee.
4. **Complete required review.** The review must name the content it examined and its dependency limits. A matching snapshot cannot manufacture a completed review. Any author correction is POST-REVIEW and receives the review required by existing UPGRADE_PROTOCOL4/4a/4b. Reuse a narrower unaffected result only where its input/claim mapping establishes that it remains applicable; otherwise recheck the bounded candidate. Do not copy the entire PROME review workflow.
5. **Pre-commit identity check.** Confirm the candidate/dependencies still match the checked/reviewed versions, and inspect per-step outcomes separately. An unrelated agent commit with unchanged relevant content does not invalidate byte identity. A changed Git-history input does invalidate the dependent result even when file bytes match. Discovery of a new candidate path requires returning to declaration; never silently hash it into a previously reviewed package.
6. **Commit exact authored paths, then verify the actual commit before push.** Capture the created commit's object ID from the commit operation; do not assume moving shared HEAD still names our commit. Read its full changed-path set against its explicit parent and compare with the declared change set plus named bookkeeping additions. Confirm each candidate blob/mode/deletion matches the accepted manifest; unchanged included deliverables must also match that commit's tree. Reject extra, missing, reverted, stage-only, unexpectedly converted or type-changed candidate content. Mere `origin/master == HEAD` is not this check. An unsupported merge/rebase or ambiguous commit identity is UNKNOWN until the exact candidate commit is located and compared. Do not amend a shared HEAD or modify foreign work to recover.
7. **Revalidate relevant dependencies before push.** Compare content/history inputs still required for a present-state acceptance; a dependency drift invalidates the affected assurance even if the candidate commit is unchanged. Pin any intentionally historical input and retain its time boundary. Shared-branch push carries reachable commits from other desks: certify only this named candidate and do not claim to have reviewed the whole push train. No atomic guarantee against changes after the last check is claimed; a stronger transaction-wide guarantee is outside this proposal.
8. **Push and verify delivery.** Use existing safe-push and fresh-origin membership checks for the exact commit. Receipt content checks use that immutable commit's blobs, not an assumption that current remote-tip files still equal the historical candidate. Later legitimate owner changes can coexist with delivered history; “delivered” and “still current at origin tip” are separate facts. A rewritten own commit after authorized recovery must be relocated and compared before its assurance is reused; never infer equivalence from its subject alone.
9. **Record delivery-only follow-up separately (POST-REVIEW R1).** A later receipt or STATUS/HANDOFF addendum may name the frozen substantive commit and verified delivery/recipient facts. It is a separately scoped commit, with checks/review appropriate to its own content, not content certified by the earlier receipt. Never require a candidate file to contain its own eventual commit hash. New findings, changed coverage or substantive dispositions re-enter applicable checks/review; they are not bookkeeping. Bind the returned independent-review report as evidence of the exact candidate it read, without requiring the report to hash or recursively review itself. This finite sequence preserves the earlier review boundary and avoids an endless receipt cycle.

No automatic commits, pushes, rebases, staging, owner launches or messages are added to the gate. Root concurrency/recovery rules remain canonical. The operator still decides the authorized action; the verifier provides bounded evidence rather than authority.

## 5. Identity, check results, review and delivery are separate

The existing `verify-receipt` remains an identity-only interface for legacy receipts; document that current VALID can describe unchanged failure. Do not silently change its rc0 into “safe to commit.” Proposed candidate verification is an explicit opt-in operation in the **same runner**, using a versioned receipt schema; exact CLI spelling is an implementation detail to settle before coding. Legacy receipts lack the new candidate/dependency/review fields and cannot be upgraded to candidate acceptance by inference. Existing boot/closeout per-step class meanings remain unchanged.

**POST-REVIEW R2 — existing caller migration:** Current mandatory `verify --subject` runs V1 (subject-based location/delivery heuristic via `verify_push.sh`) and V2 (located paths compared at moving origin/master and HEAD). Neither proves the proposed named candidate commit; V2 may flag legitimate overtaking. Until an approved patch, retain these existing calls and describe their limited evidence honestly. The bounded implementation must align SPAWN9/Git references, spec, runner CLI and relevant selftest cases so the explicit new opt-in candidate path supplies immutable commit/content verification, while legacy receipt identity and subject verification remain labelled legacy assurances. No standalone tool or `verify_push.sh` change is proposed. Settle exact CLI/schema and per-step eligibility mapping before coding; independent caller/consumer acceptance remains owed.

| Dimension | Question answered | What a positive result cannot imply |
|---|---|---|
| Content identity | Do these exact paths, operations, bytes and relevant inputs still match? | Checks passed, review occurred, or undisclosed files were covered |
| Check outcomes | Which applicable checks ran, with which native results and limitations? | Correct substantive judgment, or success for a skipped/unknown step |
| Required review | Is there an actual review receipt for these exact claims/content and applicable policy? | Approval to edit a harness or consumer acceptance |
| Commit identity | Does the named commit contain the declared reviewed/checked candidate and no undeclared package change? | Remote delivery or review of other desks' shared commits |
| Delivery / consumption | Is that commit on freshly fetched origin; did the recipient acknowledge or consume the named package? | Notification equals consumption; an older read covers later evidence |

A receipt containing BLOCKING stays blocking after any identity match. Inspect the whole per-step set: an aggregate rc2 UNKNOWN must not conceal a simultaneous BLOCKING row. DUE remains maintenance owed, not CLEAN and not automatically BLOCKING. ADVISORY, DECLARED and NOT-APPLICABLE retain their reasons. Missing review required by existing policy remains owed. A machine can verify receipt references/hashes, not whether the human/model actually performed an honest review.

UNKNOWN in a boundary input needed to certify the candidate means candidate assurance is unavailable; it never becomes a pass. Unrelated maintenance UNKNOWN remains explicitly scoped and disclosed under existing policy. **This proposal creates no blanket BOND-style prohibition on every commit/push with any UNKNOWN/DUE, and no new waiver.** Existing blocking requirements still apply. If existing authority permits delivery of a clearly PARTIAL report while an unrelated profile clock is UNKNOWN, record both facts without calling the whole closeout clean. An acceptable limitation must cite the applicable existing authority/claim boundary; the author cannot clear a blocker merely by declaring it irrelevant. Exact machine eligibility mapping must receive independent acceptance with the later patch; until then this remains UNVERIFIED-REMEDY.

## 6. Completion record in existing continuity only

Proposed compact STATUS entry, with HANDOFF pointing to that entry/package rather than restating a second ledger:

| Field | Required content for the relevant package |
|---|---|
| Work | Scope established; exact remainder/unknowns; whether the package or only a tranche is complete |
| Review | Required or exempt with source; reviewer; exact version/hash; verdict and POST-REVIEW residue |
| Checks | Receipt; blocking/unknown/due outcomes with their bounded meaning; applicable no-op declarations |
| Delivery | Exact commit and verified push, or concrete blocker; publication only where this assignment requires it |
| Recipient | Notified / acknowledged / consumed stated separately with receipts; not-applicable when no consumer is required |
| Next | Existing owner, date/trigger, concrete action and completion condition; no deadline moved by scheduling |

Applicable obligation outcomes: **updated** (path/evidence); **unchanged** (specific reason); **deferred** (existing owner, date or trigger, next action). Only obligations relevant to the session receive an outcome. Do not enumerate every untouched file, invent a date for an unscheduled owner, or add recurring follow-ups. A stated no-op is a declaration, not mechanically certified truth. This format replaces repetitive continuity prose and adds no new ledger.
