A concrete inconsistency does remain. DEWEY's TWO MODES section says cold research receives only the question and thesis research adds CONTEXT.md. Its BOOT step 3 nonetheless directs a CONTEXT.md read before step 4 gets the question and step 5 selects the mode. At the pinned revision that context file is **19,447 bytes**. This establishes an instruction-order conflict and a potentially avoidable read on cold tasks. It does not establish that a particular recent cold run actually incurred the read. An owner clarification should select mode before this conditional context load, retaining current owner evidence whenever the question needs it. No edit has been applied.

## The closeout defect is a scope mismatch

The independent [October 24 L796 read](../../../../PROME/reports/2026-10-24_L796-counterexample-read.md) names two distinct problems: unrelated post-freeze files still block the later delivery check, and the ownership rules were read from a mutable file. The first is already registered as **WQ-517**. PROME was actively repairing the second during this investigation; that work and its later acceptance state are not certified here.

I reproduced the first problem using committed code copied into disposable repositories. Every operation was sequential: freeze a reviewed result, create another desk's unrelated file, commit only the reviewed result, verify that exact delivery commit. The first verification passed; delivery verification returned 1 and named the unrelated file. No simultaneous write to one file was necessary.

| Fixture | Working-tree check | Delivery check | Interpretation |
|---|---:|---:|---|
| Reviewed result, no arrival | 0 | 0 | Clean control |
| Unrelated REGINALD file arrives after review | 0, advisory | 1, UNCLASSIFIED | Reproduced defect; foreign file absent from delivery commit |
| New unreviewed PROME file stays pending | 1 | 1 | Owner work remains blocked |
| Unreviewed PROME file added to delivery commit | 0 before insertion | 1, including UNREVIEWED ACTUAL COMMIT PATH | Delivery rejects actual unreviewed content |

All four assertions matched the expected behavior. These fixtures establish this defect and the named controls only; they are not a full gate or concurrency audit.

A short lock around each file write cannot fix this example: the operations already occurred one at a time. Preventing every arrival throughout an entire review could suppress it, but would make unrelated desks wait for PROME's review. The narrower remedy is the WQ-517 A proposal: assess the reviewed delivery and its history strictly while treating qualifying unrelated pending paths separately. OWNED, PROME-evidenced, changed reviewed content, actual delivery paths and relevant history must remain strict. Ambiguous authorship must not be presented as proven foreign ownership. The ownership-policy repair is a separate prerequisite to trusting that classification.

Other concurrency problems require different remedies. Git already uses lockfiles for atomic updates, but that does not make an agent's multi-command review-and-commit sequence one transaction ([Git lockfile API](https://git-scm.com/docs/api-lockfile)). The fleet's `scripts/orch_log.py` already holds a file lock while appending and regenerating its view. A Linux advisory lock only coordinates writers that honor it ([flock manual](https://man7.org/linux/man-pages/man2/flock.2.html)). Separate Git worktrees have separate indexes, but would require an explicit integration and shared-state design ([Git worktree documentation](https://git-scm.com/docs/git-worktree)); no migration is proposed on the strength of this defect.

## Recommendation

Keep the approved three-event trial on its existing rails. Favor WQ-517 A with its existing acceptance and independent review requirements; it addresses a reproduced obstruction and already has an owner. For research efficiency, begin with DEWEY's mode-order clarification and a bounded observation of OTTO's existing short path. Retain the deferrals on conclusion expiration and dead-end indexing. There is no measured case here for a new fleet-wide research-depth rule, database, agent or locking layer.
