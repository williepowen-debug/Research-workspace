## Verdict

The comparison correctly identifies a coordination gap: DAEDALUS has multiple checks but no unified run record of applicable steps, results and omissions. Its proposed remedies need narrowing. PROME's more elaborate process is not proof of end-to-end enforcement, and DAEDALUS is not starting from zero review machinery.

## Corrections to the comparison

1. **PROME symmetry is advisory and lexical, not guaranteed execution.** `PROME/tools/prome_gate.py:809` harvests explicitly capitalized `Read` directives and filenames from BOOT.md, then checks their names occur in CLOSEOUT's symmetry section. It records ADVISE. It neither proves every mandatory read was captured nor that an actual writeback happened. `boot_session.py` receipts one invocation per chosen run directory; it does not execute every manual boot step or certify semantic completion. PROME's boot skill itself says the spine-audit date check is outside the gate. “One-shot mechanical boot” should therefore mean the gate portion, not the entire boot.
2. **DAEDALUS already has conditional independent review.** `UPGRADE_PROTOCOL.md:74` requires a blind counterpart pass for self-audit/reflective analysis. Its rule 4 (Will-ruled September 7) concentrates independent review on triggers, grading and evidence interpretation and expressly rejects making another reviewer mandatory for routine maintenance. Rule 4a extends this to consequential remedies. There is no universal frozen-candidate closeout review, but “none; only when Will sends CATO” understates existing requirements. First reconcile and apply those rules rather than create a competing blanket rule.
3. **complete_check is more than a claim list.** It mechanically gates BLUEPRINTS/UPGRADE_PROTOCOL ↔ EVOLUTION same-commit pairing, reader-report/synthesis symmetry and EVOLUTION placement. Its claim enumeration remains judgment-only. These are narrower than full boot/writeback symmetry, but should be reused, not recreated.
4. **Subject-based push matching is not stronger identity proof.** `verify_push.sh` explicitly calls its substring-plus-age match a heuristic and asks for content verification on load-bearing checks. It warns but still returns 0 when multiple matching subjects exist. Current shared `scripts/safe-push.sh:96–106` already freshly fetches, tests HEAD ancestry and returns CANNOT-CONFIRM/2 when the fetch fails. Both desks use it. Preserve unavailable-evidence handling; do not replace exact commit verification with subject matching. Use subject search to locate a commit after a rebase, then check its expected paths/content. No simulated failure test was run in this comparison pass.
5. **DAEDALUS's battery is condition-dependent despite lacking named tiers.** Root consumer/memory checks have applicability conditions; its own map/index writes depend on actual changes. Do not turn “full battery every session” into unconditional scans or rewrites. State APPLICABLE / NOT APPLICABLE with a reason. Also `verify_push` is post-delivery verification, not a pre-commit gate.
6. **Hook absence needs a launch-scope qualification.** DAEDALUS has no local `.claude` settings; PROME has local banner/clock wiring. Root `.claude/settings.json` also contains the banner. This inspection does not establish hook behavior for every standalone, inherited or spawned session. Observe the actual launch before claiming DAEDALUS can never receive a banner. No runtime config changed.

The manifest difference is concrete: READS.tsv has 29 PROME rows and zero DAEDALUS rows (counted using the `reader` column). The root read-cap code consumes attested manifests and falls back to the charter heuristic for an absent desk. Some file-header prose still describes this as future work; actual code and current check output govern this assessment. DAEDALUS's SPAWN section is 7,523 bytes and contains substantial history. “40% narrative” was not independently measured.

## Recommended bounded design

**First: declare the read scope and shorten the instructions.** Add DAEDALUS to the existing manifest through the owning process; cover the actual runtime's inherited context, whole reads, scoped reads and conditional reads accurately. Move explanatory history to its existing archive with resolvable pointers, preserving commands, order, conditions and authority. A declaration does not prove a read occurred. Do not silently expand every-boot scope or let a declaration conceal an existing mandatory read.

**Second: one thin runner, reusing the current checks.** A `daedalus_gate.py` is reasonable only as an orchestrator: boot/closeout modes, named applicable steps, native result plus reason, and a saved receipt for a specific revision/input state. Preserve the difference between DUE work, blocking corrections, failed checks, unknown evidence and a justified non-applicable step. Do not interpret every child rc=1 identically: sweeps_due reports due work, while another tool's 1 may represent a blocking defect. Keep commit/push separate; fail/unknown must not appear as completion. A wrapper that merely prints a green aggregate is insufficient.

Acceptance before implementation: an omitted mandatory step is visible; missing/unreadable input stays UNKNOWN; a source change invalidates the associated receipt; a skipped conditional check carries a reason; a failing child cannot be hidden by a pipe; unrelated active work is untouched; a positive receipt identifies exactly what was checked. Exercise real prior failure and clean examples under CHECK_STANDARD §3. No automatic checklist edits, new checks or policy duplication needed.

**Third: make the existing review triggers usable at delivery.** Prefer “review required because this changed scoring/trigger semantics/evidence interpretation; scope, reader and disposition recorded” over a mandatory reader on every closeout. Readers must follow canonical definitions and references, and test their own counterexample. Tie the receipt to the examined changes and label later author fixes; preserve a bounded correction/residue policy. Today's false absence findings survived multiple independent readers because their briefs excluded evidence: more readers alone would not fix that.

CATO is Will-directed/manual, with permanent classification unresolved. An automatic CATO-or-ARGUS obligation would change that authority and consume review capacity; it is not implied by this request. ARGUS also has a PROME-specific contract. If Will wants a broader reviewer role, define its bounded scope separately. Likewise, self-application is a useful acceptance question for rule changes, not a reason to add an identical paragraph to every manual.

## Disposition

Recommend manifest + compact instructions first, thin receipt runner second, existing risk-triggered independent review clarified in the same plan. Do not clone PROME's publication machinery, four tiers or every-closeout audit by default. No changes implemented. Review complete; next session orient and await Will. If implementation is requested, write the concrete acceptance plan and reconcile the existing review rules before editing owner-controlled policy.
