### SP3 — gate receipt does not bind the checked inputs to delivery

**High; design defect.** Section 3a records tier, aggregate rc and the HEAD at gate time; 3b.1 checks that HEAD against the remote push base. Neither binds the receipt to the checked file contents, candidate membership or declarations (`--no-memory`/slugs, superseded figures). `commit_check.verify` checks path membership, not file contents. Section 5 explicitly leaves changed-after-gate contents to operator judgment; A10 positively permits a second commit after the gate and merely lists it.

Counterexample: gate passes at base B with `--no-memory`; later content or a memory file is added and committed above B. The remote remains B and the latest commit's filenames match its intent. The proposed Light conditions still pass without the new content/declaration having been checked. This is the very class the owner identified for `7d3325390`; printing the extra commit is disclosure, not coverage.

**Correction/closure:** bind the gate result to the actual declared delivery and relevant checked evidence, and mechanically invalidate or recheck when either changes. Reuse existing content/manifest machinery where appropriate; no blanket whole-working-tree lock or new audit is prescribed. Acceptance must reject changed-after-gate content and a late memory addition unless their required checks/declarations have been refreshed. Establish an ordinary post-commit/retry path too; matching only a pre-commit HEAD to origin can also reject valid freshly checked unpushed work. Owner PROME; unresolved.

### SP4 — Light would downgrade a known failure to advisory

**High; proposed protection regression.** Current `prome_gate.check_review_manifest` makes verifier rc=1 BLOCKING at every tier. Only the absent/prior-review case is advisory below Standard. Proposal 3b.3 treats the Light verifier as advisory generally; A6 expressly allows an UNREVIEWED addition to push at Light. The claim that no existing check changes meaning therefore does not hold for the proposed delivery decision. An old passing receipt cannot preserve the block after the candidate has changed.

**Correction/closure:** distinguish a review that is not required from a real applicable changed-content/unreviewed-addition failure. Preserve that existing block at Light/Bounce and all Standard/Heavy protections. A corresponding negative test must show no push on the existing blocking failure; do not approve A6's Light outcome as currently written. Owner PROME; unresolved.

### SP5 — HEAD-only path checks miss an earlier unreviewed commit

**High; design defect demonstrated with current functions.** Proposed 3b.2/3b.3 use the latest intent and HEAD's own paths, but `safe-push.sh` delivers every unpushed ancestor too. A10 permits two commits and claims the second's additions check covers the case. It does not cover a new path introduced only by the first commit.

Isolated reproduction: first commit adds `PROME/unreviewed.md`; second changes only `PROME/example.md` to the reviewed bytes. The latest intent contains only `PROME/example.md`. Current `commit_check.verify('HEAD', False)` returns 0; `argus_scope.verify_review(paths=HEAD_paths, ref='HEAD')` also returns 0. Giving the verifier the full candidate range returns 1 and names `PROME/unreviewed.md` as UNREVIEWED. Thus the Standard branch as proposed can bless a push containing an unreviewed earlier PROME addition even while its HEAD check passes.

**Correction/closure:** establish complete membership of PROME's intended delivery across the outgoing range, with an explicit disposition of any other owners' carried commits; check the committed contents at a named tip and define what happens if that tip moves. This does not grant CATO/PROME ownership of other desks' content or require ARGUS to audit the whole fleet. The two-commit counterexample must refuse; ordinary reviewed multi-commit delivery should remain usable. Owner PROME; unresolved.
