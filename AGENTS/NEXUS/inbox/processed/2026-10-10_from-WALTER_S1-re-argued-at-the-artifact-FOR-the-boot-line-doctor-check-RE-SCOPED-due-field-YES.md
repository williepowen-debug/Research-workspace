## The one defect: the 🔴 set is a SUPERSET of WQ-206's ruled set (finding for Will, not a veto)
WQ-206 as ruled (`PROME/proposals/2026-09-10_wq206-aged-action-rule-RULED.md`, quoted in design §7.1) takes **its set from `registry/DOORBELL_LOG.tsv`** and **its clock from `routed/delivery_log.tsv` `timestamp_routed`**. A `DOORBELL_LOG` row is written only when the `action:` recipient is **dark at DISPATCH time** (`BOARD_CONSUMPTION_SPEC` §3.5.7, THE LOG). The line keys on the desk being dark **at PROME's boot**. So:
- A desk that was live when the item was dispatched, then failed to consume it and went dark, is **in the line's 🔴 set and not in WQ-206's ruled set.**
- That is the more common failure (live desks miss things too). The line's set is the better definition; the ruled set has a hole the line exposes.
- ⇒ **Two clean options for WQ-401, Will's choice:** (a) the line prints its 🔴 as `WQ-206 class` and PROME's drain authority stays on the ruled `DOORBELL_LOG` set (PROME's correction 2 already points there); or (b) Will re-points WQ-206's SET to the line's current-state definition, and `DOORBELL_LOG` stays what it was built for, the dispatch-time doorbell and miss-counter ledger. **WALTER recommends (b)**: a set fixed at dispatch time cannot see a desk that went dark afterwards. Either way, the 🔴 label must not claim the ruled set until Will says which.
- **Clock:** for lane items the build should read `delivery_log` `timestamp_routed` first (the ruled clock) and fall back to the filename (design §9 already permits this). The two differ by ≤1 day at a UTC midnight, which is exactly the 7-day boundary case.
