| # | Name | Type | Purpose |

| 2 | `fired_date` | YYYY-MM-DD | When WALTER auto-dispatched on this trigger |
| 3 | `metric_value_at_fire` | Numeric | Recorded value that triggered (post-sustain-window confirmation) |
| 4 | `dispatched_signal_id` | String | SIG-W-YYYYMMDD-NNN generated by WALTER |
| 5 | `sustain_confirmation` | Integer | Number of sessions confirmed in sustain_window (typically equals `sustain_window` from the trigger row) |

## Operational pattern

1. **At boot (spawn-protocol step 6b):** WALTER reads `AGENTS/RED/registry/FALSIFICATION_TRIGGERS.tsv` into memory. Reads `FALSIFICATION_FIRED_LOG.tsv` for fire history.
2. **At dispatch session-end (CHECKLIST Phase 2 step 7):** for each RED trigger, query `FORGE/tools/market-data/fetch.py` for live metric. Apply threshold + sustain window. If sustained-cross confirmed AND not stale-fire-suppressed (lookup most recent `fired_date` per trigger_id; if within `sustain_window` sessions, skip), auto-generate signal per `recipient_chain`. Append fire row to this ledger.
3. **Stale-fire suppression:** per JOINT_PROPOSAL §2.2 step 1 — prevents repeat-fire on persistent crosses. RED's adversarial-overlay only needs the first-cross signal; subsequent persistence is BRENT/HAWK/LIQUID-domain re-coverage territory.
4. **Approaching-threshold (within 5% one-sided per `threshold_op`):** flagged in WALTER closeout SESSION LOG as "near-trigger watch", not auto-dispatched. RED + Will see proximity without dispatch noise.

## Why parallel ledger, not write-back

Per Critical Rule #2 (subagents own their files), WALTER does NOT write back to `AGENTS/RED/registry/FALSIFICATION_TRIGGERS.tsv`. Fire history lives here in WALTER's tree. RED reads this file at boot if RED needs to see fire history; otherwise it's WALTER-internal eval state.

Same pattern as the proposed CHG-RED backfill (WALTER produces a diff at `AGENTS/WALTER/handoff_RED/CHALLENGES_BACKFILL_diff.tsv` for RED to apply at his next boot — see JOINT_PROPOSAL §7 #4).

## Out-of-scope (v1)

- Continuous live-tape polling (WALTER not always-on; eval at session-boot or explicit dispatch only)
- Multi-leg compound triggers (no AND/OR composition; each row independent)
- Event-type triggers (5 event-type triggers per RED Turn 3 honest gap — WAL MI3 / BTFP 2.0 / OZK NCO / bypass-pair / etc. — stay in `AGENTS/RED/CALENDAR.md` FALSIFICATION WATCH; manually checked by WALTER at closeout)

Schema v2 with `trigger_type: THRESHOLD_CROSS | EVENT_PRINT | DISCRETE_ANNOUNCEMENT` discriminator deferred until v1 operational + coverage gap data accumulates (RED preference; WALTER concurs).
