**Finding (2026-07-16):** during the post-offline-gap catch-up, TERRY re-attributed the GATE-VIO-116 fire from F3→F1 based on Yahoo's `^MOVE` 1h-bar endpoint (`interval='1h'`), which returned degenerate single bars (OHLC identical) labeled 7/13=69.55 / 7/14=77.77 / 7/15=75.03 — **the whole series shifted one day late** (69.55 was actually the 7/10 close). Simultaneously PROME's daily-close pull showed the feed had **stopped posting entirely after 7/10**. PROME held the canon edit pending a source; TERRY web-verified the true dailies (investing.com: 7/13=77.77 +11.82% / 7/14=75.03 / 7/15=68.48), which **tied arithmetically to the last PROME-verified anchor** (69.55 × 1.1182 = 77.77 ✓) — the spike was Mon 7/13, F3 was correct all along, and the retraction landed before anything false entered GATES.

**Why it matters:** the mislabel didn't look broken — it returned plausible values on plausible dates. On a sparse index the two failure modes compound: no fresh daily to cross-check against, and an intraday endpoint that quietly reuses stale closes under new labels. A gate attribution (WHICH condition fired, WHEN) was nearly canonized wrong.

**How to apply:** (1) For sparse-feed tickers (^MOVE, ^SKEW class): treat Yahoo daily history as *last-posted*, not *current* — check the max date before trusting; never use 1h/intraday bars as daily-close substitutes. (2) Any load-bearing print from a secondary source must be **arithmetically tied to a verified anchor** (chain the %-changes back to a close you've already exact-matched) — that tie-out is what turned an unverifiable web number into canon-grade. (3) Coordinator rule: when an agent's correction hinges on a data print you can't reproduce from your own primary, ask for the exact source/endpoint BEFORE amending canon — the 10-minute round-trip caught this. Related: [[finding_quote_carries_data_minute]], [[finding_tool_default_asof_date_drift]], [[finding_ohlc_verify_before_session_claims]].

**n+1, 2026-08-02 — the class extends to FX PAIRS (`=X`), and it had shipped a silent wrong number into a live tool.** `FORGE/tools/market-data/fetch.py` rendered USD/JPY at **−2.40%** against a true **−0.68%**. Mechanism: `fast_info.regularMarketPreviousClose` is *always the second-to-last daily bar*, which is correct for equities/futures/indices — but Yahoo's **FX daily bars are date-shifted**, so the bar labeled 7/31 closed 160.183 while Friday's real close (157.395, verified 3 ways) appeared as the **OPEN of the next bar**. Same signature as the ^MOVE case: plausible values on plausible dates, nothing looks broken. Sharper diagnostic than 2026-07-16's, found independently by SAM: on FX bars **Open ≈ Close on every row** — they are bar-boundary snapshots, so the Close field carries no information. Fixed FX-only (`=X` → chart-metadata `previousClose`, which reproduced the 3-way-verified close exactly); non-FX deliberately untouched.

**Two lessons this instance adds:**

**(a) An unanchored denominator is the vulnerability, not the bad datum.** The wrong figure survived because the surface stamped the *price* (`asof`) but nothing stamped **what the change was measured against**. A percentage with no basis date cannot be audited by a reader — it can only be re-derived from scratch, which nobody does. Fix shipped alongside: a `prev_asof` basis stamp. **Generalize: any derived metric (change, spread, ratio) should carry the vintage of BOTH sides, not just the one you happened to fetch.** Cf. [[finding_number_carries_threshold_unit_source]].

**(b) ⚠️ A verification whose ground truth comes from the instrument under test cannot falsify it — it will CONFIRM the error.** My first check compared both candidate fields against a "true prior close" I derived from *the same daily-bar history that was shifted*. It returned a confident, clean verdict — **`regMkt closer` for JPY=X** — i.e. it endorsed the wrong field, and a global field-swap shipped on that basis would have regressed every non-FX ticker. It only broke open when the result was tested against an **independent** anchor (investing.com, and the fleet's own 3-way-verified 157.395). **Before trusting a verification, ask where its ground truth came from; if the answer is the same source/feed/parser you are testing, it is circular and its agreement is worth nothing.** The tell is a test that agrees *too* cleanly across every row. Cf. [[finding_circular_corroboration_via_state_file]] (same failure shape, state-file substrate), [[finding_verify_recommended_fix_not_just_finding]], [[finding_freshness_check_cannot_catch_a_fresh_lie]].

**Stakes note:** the bad print sat adjacent to a Will-gated capital trigger — GATE-SAM-30's early-entry override is a *≥2%/day disorderly yen move*, so **−2.40% read as THROUGH the line when the real move was −0.74%.** Nothing fired (the discrepancy was caught on a routine boot pull), but the failure mode is "tool quietly manufactures a trigger," not "tool is unavailable."
