**Incident (2026-07-09 discovery, 2026-07-02 failure):** VIOLET's KB-VIO-110 registered "any ONE gate fires the same-session tail-hedge packet-build." Both gates (CCC persistence + LIQUID breadth confirm) resolved FIRED the morning of 7/2 — the same morning VIOLET's session froze. The consequence (build VIX-call packet → Will [Approve]) lived only in VIOLET's own KB, so no other agent's boot could see the fired gate. It sat orphaned 7 days until the 7/9 backfill spawn audited the window. Will never saw the proposal he was owed (failure was upstream of his decision; the missed hedge happened to be flat-to-down — cheap lesson).

**Why:** file-based coordination means an agent's own KB is invisible to the rest of the fleet between its sessions. A gate registration is a *promise of future action*; promises stored only with the promisor die with the promisor's session.

**How to apply:** every gate whose FIRE requires an action (packet-build / arm / proposal / route) gets a row in `PROME/GATES.tsv` (the fire-ledger) **the same session it's approved** — PROME boot (BOOT.md step 3) scans it: `FIRED-UNEXECUTED` = blocking; `last_checked` >5d on a LIVE row = refresh/flag. Graded-later predictions stay in agent PREDICTIONS ledgers (don't duplicate). Owners' KBs stay canonical for full gate logic. Related: [[finding_asymmetric_records_need_reconciliation]] (sibling class — diverging records; this one is *invisible* records), [[feedback_deploy_on_trigger_not_calendar]].

**VALIDATED IN PRODUCTION (2026-07-16):** the fleet went dark 7/13-7/15 (usage limits) and TWO registered gates fired into the gap — GATE-TERRY-ARM2 (10Y 5-of-5 completed Mon 7/13) and GATE-VIO-116 (F3, same day). The first boot after the gap caught **both within minutes** via the BOOT.md step-3 GATES.tsv scan; both were flipped FIRED-UNEXECUTED, escalated to Will same-message, and had their consequences executed the same session (card armed + Will decision; shape memo delivered). Contrast with the founding incident: 7 days orphaned vs ~0. The ledger's value case is now empirical, not theoretical. Corollary learned same-day: the ENERGY re-arm condition lived only in HEARTBEAT/ACTIVE_DECISIONS *prose* (no GATES row after the 7/10 DENY resolved its row) — it also "fired" into the gap but had no ledger row to catch it, and was recovered by narrative reconstruction instead. **Rule sharpened: when a gate RESOLVES with a defined re-arm condition, register the re-arm as its own LIVE row — prose re-arm conditions are the same invisible-promise class.**

**EXTENDED (2026-08-16, FERT revival assessment — the DORMANCY limb, n+1):** the ledger only protects gates registered INTO it, and the largest hole is agents that pre-date it or go dormant carrying live thresholds. FERT (dormant since 3/20, ARCHIVE SOURCE) held a registered RED line ("urea NOLA >$800 = triggers food CPI chain") in its own STATUS. The line breached ~8 weeks from late March (on the benchmark it was actually tracking — a separate mislabel finding), WALTER escalated "revival-worthy" into its inbox TWICE (6/26, 7/6), and nobody was accountable for grading it: the gate never had a GATES.tsv row, and a dormant desk's inbox is write-only. Discovered 8/16 only because Will asked about reviving the agent. **Rule sharpened: DORMANCY IS A REGISTRATION EVENT.** When an agent goes dormant/archive (or at the first sweep that finds it so), its live registered thresholds must either (a) move to `PROME/GATES.tsv` with a named grader, or (b) be retired/bannered dead — a threshold with no assigned grader is a silent instrument regardless of how loudly it fires. One-time fleet sweep for the class routed to DAEDALUS 8/16 (dormant/archive dirs, grep for un-ledgered trigger language).
