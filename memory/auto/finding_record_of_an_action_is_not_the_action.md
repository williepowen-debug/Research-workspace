**A record about an action is not the action.** This holds for other agents' records *and for your own* — the second is the one that gets through, because you trust your own commit messages.

**Two instances, 2026-07-27, both PROME's, ~5 hours apart.**

1. **Someone else's record.** CREED's memo said a REGINALD freeze-banner ask was *"still pending"* — 23 days open. PROME relayed it to Will and cited the root Data Hygiene rule at it. **REGINALD had satisfied it 18 days earlier** (`da82a095`, 7/09), and the banner was *better* than the ask required. The stale claim lived in **CREED's own records** (`LAST_COMPLETION.md`, `STATUS.md`), written 7/4 and never refreshed. Three hops, one unchecked predicate.
2. **My own record.** The HEARTBEAT re-base commit stated a VIX-COT decay finding was **"Routed to VIOLET."** No such packet existed. I had written the intent in a commit body and never created the artifact. Found only because I checked VIOLET's inbox before writing a follow-up — **while VIOLET was booting to mark a live position with a mandatory exit two days out.** The two available framings of that datum pointed in *opposite* directions, so the missing half was decision-relevant, not cosmetic.

3. **A third party's record of their own intent, relayed.** *(Added 2026-07-28, PROME again.)* VIOLET's 7/27 close memo said it had **"asked HENRY for a fresher flip."** PROME relayed this into SCRATCH, STATUS and HEARTBEAT as *"VIOLET asked HENRY; HENRY has not answered"* — manufacturing an owed-item against HENRY. **No VIOLET→HENRY packet ever existed** (verified 7/28: not in HENRY's inbox or processed, not in VIOLET's outbox — the "ask" was prose in a memo to PROME). HENRY checked its inbox before acting on PROME's directive, found no ask, said so, **and delivered the answer anyway** because the deliverable was right independent of the request. New edge: **the requester's *stated intention to ask* is even weaker than a requester's "still pending" — it records a plan, not a send.** When relaying "A asked B," verify the packet in B's inbox first; otherwise write "A intends to ask B" and route it yourself.

4. **Your own record of a FIX — the declaration that stops anyone looking.** *(Added 2026-07-28, BRENT. n=4, and the most expensive shape.)* BRENT's USO call spread **filled 7/24**; STATUS and TRADE.md carried it as PENDING until 7/27. On finding that, BRENT wrote a hygiene note **declaring the contradiction fixed** — and had corrected only the **execution-log row**. The TRADE.md header, a TRADE.md narrative line, and **`NEXUS_BRIEF.md:61`** all still said *"pending fill."* NEXUS reads that brief **in place of** BRENT's STATUS at its boot, so **a live money-committed position was reported to a consuming agent as un-filled for four more days**, now under cover of a written statement that the problem was solved. Found 7/28 by a DAEDALUS architecture audit — **not** by BRENT's own closeout sweep, which had read the note and moved on.

   **The generalisation: "declared fixed but only partly fixed" is worse than "open."** An open defect still attracts attention. A *declared-fixed* one is actively defended by its own record — the note is the newest, most authoritative artifact, it is written in the voice of the person who did the work, and it converts every future reader (including the author) from *checking* to *trusting*. **Same mechanism as the three cases above, one turn worse: the record doesn't just substitute for the action, it immunises the gap against discovery.** Cousin to [[finding_freshness_check_cannot_catch_a_fresh_lie]] — there a *fresh* file is false; here a *fix note* is partial. Both defeat the check that would have caught them.

   **Apply:** when you declare something fixed, **enumerate the surfaces and re-grep for the defect string**, don't fix the instance you happened to be looking at. `grep -rn "<the wrong string>"` over your whole directory costs seconds and is the entire check. And **scope the claim to what you verified** — "fixed the execution-log row" is true and safe; "fixed the PENDING contradiction" was neither.

**Why it survives every reader:** these records are *assertions in the voice of the system of record.* A commit message is written by the person who would have done the thing, at the moment they intended to; a requester's status file is written by the person who wanted it. Neither is updated by the event that would falsify it. Nothing in the pipeline re-checks them, so they propagate at full confidence.

**How to apply:**
- **Before re-raising an aged cross-agent ask:** `git log` the **target path**, not the requester's note. The requester's record of an ask is not evidence the ask is open.
- **Before citing your own routing/delivery as done:** `ls` the **recipient's inbox**. "Routed", "flagged to", "notified" in a commit body are intents until an artifact exists at the destination.
- **Highest-risk moment:** a *crashed or interrupted session*. Intent-language survives in commits; the artifact-creating step is what gets lost. After any unclean shutdown, re-verify every delivery the dead session claimed.
- **Cheap tell:** if the only evidence for X is a sentence written by whoever was supposed to do X, it is unverified.

**n=6 — THE SELF-DIRECTED FORM: "I verified it" is itself an unverified claim (BRENT, 2026-08-02).** All prior instances are about a record of an action *someone was supposed to take*. This one is narrower and harder to see: **the asserted action is the VERIFICATION ITSELF.** BRENT froze a pre-registration and wrote that its baseline *"−7.75% … **reproduces on my own OHLC**."* It did not. The figure had been back-solved from an **intraday 12:58 PM quote lifted out of BRENT's own earlier prose** rather than the session close; the true value was **−8.70%**. **The four words "reproduces on my own OHLC" were doing all the evidentiary work and nothing behind them had run.** Aggravating detail that makes the pattern legible: it was written **inside the same document where BRENT was correcting another agent for an intraday-as-close error and correcting its own vol figure for the same class** — i.e. the verification language got *more* confident precisely where the surrounding text was about verification failure.

**Why this form evades every existing guard:** a delivery check can ask "does the artifact exist?", and an audit can ask "was the step run?" — but a *verification claim* has no artifact and leaves no trace. It reads as the strongest kind of sentence in a document (a first-person, self-audited confirmation) while being the cheapest to fabricate by accident, because re-reading it **feels** like checking it.

**Apply:** never write **"verified" / "reproduces" / "confirmed" / "checked"** unless the command that produced it **ran in the current session** — if you are recalling that you checked, you did not check. **And prefer to paste the derived number's inputs** (dates + both endpoints), because an input pair is falsifiable by the next reader and an adjective is not. Corollary found in the same session: the error surfaced only because BRENT went to **pull data**, never from re-reading — **so when a claim is load-bearing, re-deriving is the check and re-reading is not.**

**n=14 — THE INSTRUCTION FORM: an instruction is written against an ASSUMED state, so obeying it literally can CREATE the defect it exists to prevent (CREED, 2026-08-28).** Every limb above is about a *record* and an *action* disagreeing. This one is about an **instruction** and the state it presumes. A coordinator packet told CREED, at its next boot, to *"record the T-06b fire on your own ledger"* — written the evening before, in good faith, by a desk that could not see CREED's registry. **The fire had already been entered, with all three of its dates, in the same session that adjudicated it hours earlier.** Executing the instruction as written would have produced **a second fire row for one event** — precisely the "two ledgers that disagree" defect the receiving desk had *itself refused* weeks earlier when another agent offered to mirror its fire log. **The instruction was correct when written, correct in intent, and would have manufactured the exact failure it was meant to close.**

**Why this form is uniquely easy to walk into:** the other limbs punish *trusting* a record. This one punishes *obeying* one, and obedience feels like the safe, humble choice — especially for a subordinate or spawned session, where "do what the packet says" is the whole contract, and where re-reading the packet (rather than the artifact) feels like diligence. **An instruction carries no timestamp on the state it assumes.** The gap between authoring and executing is exactly where the state moves, and cross-desk instructions are authored *because* the author cannot see the target.

**The tell that saved it:** the boot sequence read the target ledger before the inbox packet was acted on, so the existing row was visible at the moment of decision. **The corrected act was a CONFIRM, not an ENTRY** — annotate the existing row with what the instruction actually wanted recorded (here: the three dates and an explicit "no capital path"), and report back that the state differed from the one assumed.

**Apply:** before executing any instruction that says *create / record / send / file / fix*, **open the target artifact and check whether it is already there.** If it is, do the smallest edit that satisfies the instruction's *intent* and **tell the sender the state differed** — the sender is holding a stale model and will keep issuing against it otherwise. Never resolve the mismatch by adding a duplicate; a duplicate is indistinguishable from a disagreement to every future reader. Symmetric duty on the sending side: **write the instruction conditionally** ("if not already recorded, …") and name the artifact you expect it to be missing from, so the recipient can discharge it by verification rather than by writing.

⭐ **The gate suite was FULLY GREEN on a file git had never seen.** `check_memory_length.sh` passed (18,237 B, 71% of cap). The index row was well-formed with a good hook. The body was 5,390 B of real content. **Three independent checks, three green lights, and not one of them asked whether the artifact was tracked.** A suite can be complete with respect to every question it asks and still certify an artifact that does not durably exist.

🔑 **The root cause was worse than a forgotten `git add`, and it is the reusable part.** REGINALD did not skip the commit — it believed the file was **outside the repo**. Its system prompt names the harness path `~/.claude/projects/<slug>/memory/`, so it reasoned *not in the working tree ⇒ no git concern* and never resolved the path. **It is a symlink to `memory/auto/` — same inode (verified 111773).** So the reasoning was clean and the **referent** was wrong, and every check it ran passed *against a directory it had mis-identified* ([[finding_instrument_reports_clean_against_the_wrong_reference]]). This is why "I checked" felt true and was.

⚠️ **The asymmetry that makes this class expensive here:** `MEMORY.md` is a shared index that ships out on **whoever commits next** — any agent, or the push-train — while the memory FILE needs its own deliberate `git add`. So the window between "row written" and "file committed" is a window in which *someone else's unrelated commit* publishes a pointer to nothing. An index row with no body is worse than no memory: it advertises a slug that cannot be read, and the reader cannot distinguish *missing* from *never written*.

**⇒ The remedy, as a COMMAND rather than a disposition** — REGINALD's own framing, and the reason it is worth writing down: *"check the artifact"* is a disposition it **already held** and it did not fire. Run **`git ls-files --error-unmatch <path>`** before claiming any durable artifact exists. For memories specifically, `scripts/memory_index_check.py --strict --slug <name>` is the gate that asks the tracking question — and it was skipped, not failed.

**⇒ And the one-line generalisation: GREEN GATES ARE NOT EXISTENCE.** When you add a gate to a suite, ask what the suite would still certify if the artifact were absent entirely. If the answer is "everything," no member is asking the existence question.
