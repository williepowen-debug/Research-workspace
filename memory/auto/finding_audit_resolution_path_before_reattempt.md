When a tracked question survives multiple sessions and each session records the *same* resolution path ("needs a court-docket pull", "needs the X API", "check ticker Y"), the recurring failure is far more often a **defect in the path** than an absence of data. Audit the path itself before re-running it.

**Worked case (STUE, 2026-07-25).** "AFT v. MOHELA — what happened at the May 28 status conference?" sat open **46 days** across three sessions, each restating the path as *"CourtListener, docket 1:25-cv-00802 — not web-searchable."* All three failure modes were present at once:
- **Wrong identifier** — `1:25-cv-00802` matched six unrelated cases and no AFT case. It had been carried forward unverified.
- **Stale venue** — the record said D.C. Superior Court (a state court, correctly noted as *not* in RECAP), but the case had been **removed to federal court** long before. The "structurally inaccessible" conclusion was true of the old venue only.
- **Unverified premise** — the May 28 conference itself was never on any docket; it came from an SEO legal-aggregator page. The question was partly asking about an event that did not occur.

Once the actual case was found (`D.D.C. 1:24-cv-02460`), it resolved in one fetch — and the answer *inverted the read*: discovery had been **stayed by court order** for nine months. The parent agent's standing note, "absence of news is non-information," was exactly backwards.

**Apply:**
1. **Verify the identifier before re-spending on the lookup.** One cheap existence check (does this docket/ticker/ID resolve to the thing I mean?) beats another failed pull.
2. **Re-check the venue/owner.** Cases get removed or transferred, series get renamed, endpoints move. "Not accessible" is a claim about a *location*, and locations go stale.
3. **Test the premise.** Before asking "what was the outcome of event E", confirm E happened. A well-formed question about a non-event never resolves.
4. **Silence with a mechanism is information.** A quiet docket, empty queue, or flat series may be quiet *by order or by construction*. Find the mechanism of the silence before scoring it as no-signal — a stay, a pause, or a publication lag each mean something specific and different.

**It recurred in the same session — that is the important part.** Hours after writing this memory, I closed out reporting the stay order's basis as *"PACER-gated, ~$0.30 to resolve."* It was not gated at all: the docket carried **free RECAP PDFs** for neighbouring entries, and the very next filing (a joint status report) quoted the stay's purpose verbatim — *"to allow the parties time to explore a negotiated resolution."* Recovered at **zero cost**, and it materially changed the read: the case was in **settlement talks**, not a procedural freeze, which meant the evidence the prediction depended on was likely to be negotiated out of existence rather than merely delayed.

The failure mode is identical to the first: **declaring a path closed by inspecting only the obvious surface.** First time it was "the docket number I was handed"; second time it was "the button that says Buy on PACER." Neither is the whole access surface. Before recording *anything* as gated/paywalled/unavailable, **enumerate the access surface** — free mirrors and archives (RECAP/CourtListener, SEC full-text, FRED ALFRED vintages), adjacent documents that *quote* the target, and the possibility that the item has no separate document at all (a **minute order** has no PDF and cannot be bought — its text lives in the docket report or in later filings that cite it).

Corollary for aging trackers: a question's **age is itself evidence about the path**, not just about the world. Past ~2–3 failed attempts, stop re-running and start debugging the instrument. And note that "I checked and it's unavailable" is a **claim requiring the same rigor as any other** — it is the one conclusion that stops all further inquiry, so it deserves more scrutiny than a positive finding, not less. **n+1 with a new limb (PROME, 2026-08-12): the server's own error text can MISNAME the gate — do not let the error message diagnose itself.** BRENT's `EU-STORAGE` instrument sat 🔴 `NO_INSTRUMENT` for 10 days on GIE AGSI+'s error `"Invalid or missing API key"`, and the fix was registered as a Will-action queue row (get a key). The actual discriminator was the **User-Agent**: the identical URL returns full data keyless under a browser UA, and DEWEY's DR-4 pulled five years of it the same evening — its repro footnote *"(no API key required; browser UA advisable)"* refuted the standing blocker, and PROME's curl reproduced both sides of the gate in two minutes. The error text was treated as a diagnosis when it was only a denial. **Apply:** before registering any blocker off an API error message, vary the cheap request dimensions (UA, Accept header, auth-absent vs auth-present) once each — the sibling of `[[finding_edgar_403_user_agent]]` and `[[finding_blocked_mirror_is_not_an_unreachable_primary]]`, and the same shape as a court clerk's "sealed" stamp on a document that is merely misfiled. *(Closure stamp, PROME 2026-08-13: the 🔴 is CLEARED — BRENT reproduced both legs itself, wired the browser-UA as `gie:` probe grammar with a `total==0` fail-loud guard, and its blocking-instrument count went 1→0; the official free key remains the robust path, queue row 37 hardening-only.)*

**n+2, and it is the mirror limb (SAM, 2026-08-14): the request can be MALFORMED and the server answers it CORRECTLY. Twice in one session, two different desks' registered paths.** The 8/12 limb above is *"the error text misnames the gate."* This one is the opposite failure: **there was no gate at all, the URL was simply wrong, and a truthful 404 got recorded as a fact about the world.**

- **BOJ current-account archive.** STATUS carried *"the `jd` ARCHIVE PATH ITSELF APPEARS DEAD, not merely unpublished"* after **n=3 failed sessions**, and escalated it — the SAM-39 base rate (n=62) had been *measured* from that archive, so the note also declared that base rate **"not currently reproducible."** Actual cause: the request omitted the **`<YYYY>` subdirectory**. `…/d_release/jd/jd20260804.xlsx` → **404**; `…/d_release/jd/**2026**/jd20260804.xlsx` → **200**, as do five other sampled dates. **Not a UA problem — bare `urllib` retrieves it.** ⚠️ **The specific trap: a correction had fixed the *sibling* half of the distinction and silently broke this one.** The `jp` (projection) and `jd` (archive) series differ in **two** ways — perishable-vs-durable **and** no-year-subdir-vs-year-subdir. An earlier "SERIES CORRECTION" propagated the first difference and pattern-matched the path off `jp`. **Six days lost, plus a live prediction's base rate written off.**
- **FRBNY FX quarterly, same session.** The docket row warned *"site 403s the default fetcher — use curl + browser UA"* (i.e. it had already been diagnosed as the 8/12 limb). It does not 403. The registered index path `/markets/quarterly_reports` **302s to `/errors/404`**; the real path is **`/markets/quar_reports`**. **A bad path wearing a block's clothing sends you hunting for a UA workaround instead of a URL** — and the previous session's plausible-but-wrong diagnosis is what kept anyone from re-reading the string.

**Apply — before recording any endpoint as dead, moved, or blocked:**
1. **Test a KNOWN-GOOD item on the same path first.** One historical date/ID that definitely exists separates "path broken" from "this item absent." Both cases above collapse in one request under this test, and neither session ran it.
2. **Distinguish the failure codes — they mean different things and only one is about the resource.** `000`/connection = wrong host (`boj.or.jp` without `www.` fails here). `404` = your string, well-formed, names nothing. `302 → /errors/404` = wrong path, **not** a block. `403` = a gate. `200`-with-HTML-body or `200`-with-`total:0` = a lie (see `[[finding_partitioned_source_returns_stale_window_at_200]]`).
3. **When you correct one half of a two-part distinction, re-verify the other half.** A correction is the highest-risk moment for the *un-corrected* attribute, because everyone now trusts the freshly-audited line.
4. **A repeated identical failure is evidence about the REQUEST, not the resource.** n=3 identical 404s is not three witnesses that a file is gone; it is one witness, consulted three times, that a string does not resolve. **Past ~2 attempts, diff your URL against a working one character by character before writing anything down about the world.**

**Why this one is expensive out of proportion to the fix:** a "dead endpoint" note is *load-bearing downstream* — it retired a base rate, marked an intervention-ladder leg permanently unverifiable (*"only remaining independent read = MOF monthly"*), and shaped three sessions of planning. Recovering the path recovered **final actuals for all three ladder legs**, one of which matched a wire's reported figure to the decimal. **The cost of a wrong access-claim is not the failed pull; it is every conclusion drawn from the absence.** Related: `[[finding_unfetched_is_not_unavailable]]`, `[[finding_blocked_mirror_is_not_an_unreachable_primary]]`, `[[finding_claim_outlives_its_discredited_instrument]]`.
