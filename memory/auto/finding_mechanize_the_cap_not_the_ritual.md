Two instances, same shape, one agent.

**(a) Summary-doc caps rotted invisibly.** Two weeks of Tier-1 (light) closeouts left WALTER's `STATUS.md` at **12 stacked leads / 100KB** against its own 5-lead cap, NETWORK AWARENESS **5 days stale**, and **16 registry-lag rows**. None of it self-alarmed — because only the **DATA** layer was mechanized (BOARD reconcile, version drift, log reconcile), not the **SUMMARY-doc** layer. The fix that actually held was not "remember to do Tier-2": it was adding a `status_spine_overflow` check to the boot doctor so the cap alarms itself (LOW at 6-8 leads, MED at 9+).

**(b) The cobbler's-children gap.** A 6-agent self-audit found `CLAUDE.md` four spec-versions stale (BOARD_CONSUMPTION v0.2 in the doc vs v0.6 on disk), a 530KB unreadable BOARD INDEX, and push-state wrong in three documents — **none watched by the doctor**, whose checks covered the data layer but not the agent's own instruction/summary docs. Same-session fix: **+4 doctor checks** (`claude_md_version_drift`, `log_reconcile`, `cushing_capability`, `staleness_sweep_overdue`), so the drift now self-alarms at boot.

**Why:** a deferrable maintenance step is, by construction, the thing a busy session defers. The discipline that says "run the full closeout every 3rd light one" is enforced by the same attention that is already saturated — so it fails precisely when load is high, which is when the state matters most. **Self-correcting beats periodically-audited.** A periodic audit also has a hidden cost: it finds the problem *once*, then the same class re-accumulates (registry_lag was fully cleared and back to 11 MEDs in **5 days**, because active agents commit daily).

**(c) The strongest version: WRITING THE LESSON IS ITSELF A RITUAL, AND IT FAILS THE SAME WAY.** *(BRENT, 2026-08-10, n=3 on one defect.)* After Will retired a gated position arm on 8/7, BRENT ran a verification grep, reported clean, and PROME found three surfaces still carrying the arm as pending. BRENT then wrote the corrective lesson explicitly — *"when a spec's STATUS changes, grep the PENDING/FORWARD vocabulary (`due`, `by <date>`, `runs to`, `awaiting`), not just the LIVE vocabulary."* **Three days later a fourth residue surfaced: the arm's own `Status:` field still read `ARMED … expires 8/13`** — i.e. LIVE vocabulary, on the canonical trade surface, in the single most load-bearing place for it to be wrong. **The lesson had been written, re-read at boot, and reproduced anyway.**

**And a mechanized guard DID exist and passed clean three times** — a boot step requiring every `PENDING`/`⏳` row to be resolved-or-reaffirmed. **It reads EXECUTION LOG rows only**, so it never looked at section status fields. ⇒ **a guard's SCOPE is the thing to audit, not its output; a clean pass certifies where it looked, not that you are safe** ([[finding_verification_zero_is_ambiguous]]).

**⇒ THE RULE THIS ADDS: count your own repeats. If you have written the same corrective lesson N times and reproduced the defect N times, stop rewriting it — the lesson is not the fix.** Writing a lesson is enforced by exactly the attention that was already saturated when the defect happened, so **prose scales worse than a check**. Convert it into (i) a new guard, or (ii) a **scope extension of the guard that already passed clean over the wrong thing** — the second is usually cheaper and is the one people miss, because a passing check does not look like a gap.

**How to apply:** when you catch a stale doc, a breached cap, or a drifted pointer, **do not just fix it** — ask whether a check could have caught it, and add the check in the same session. Extending the doctor is the durable fix; re-auditing is not. **If a check already runs and did not catch it, the answer is almost always to widen its SCOPE, not to add a second check** (retirement-ratchet friendly: extending supersedes nothing and costs no new attention). Corollary for anything version-pointed: bump the spec → sweep the pointer doc **in the same commit** → let the guard confirm.

**(d) THE CHEAPEST INSTANCE OF ALL: A RULE ALREADY WRITTEN AS AN ARITHMETIC COMPARISON THAT NOTHING COMPUTES.** *(VIOLET, 2026-09-04, n=3 on one desk.)* A session crashed between its `STATUS.md` commit (10:06) and its write-back tail, leaving three handoff surfaces at their 08:47 commit — **79 minutes stale**, each read by a consumer who was *not* the authoring agent (its own next boot · the coordinator · the synthesis agent). At the next boot **four separate checks ran green over it**: the 14-stage boot kit, the ledger-staleness pass, the corrections check, and the closeout guard. **The rule was not missing.** The agent's own `CLAUDE.md` stated the ordering constraint in explicitly checkable form — *"the brief's commit timestamp >= the session's last STATUS commit timestamp"* — **a comparison of two integers, sitting there as a sentence for 31 days.** Ten minutes of code closed it permanently.

**⇒ A GREPPABLE AUDIT HEURISTIC, and the highest-yield one in this memory.** Do not ask *"is there a rule?"* — ask **"is there a rule already stated as a comparison, a count, a date-diff or a threshold, that no code evaluates?"** Those need no drafting, no negotiation and no ratification; they need only someone to notice. The same desk had already found two (enums "validated" by remembering — 11 rows violating, one for **109 days**; a registered mechanical re-arm line inherited as a fresh judgement call — **3 sessions** booting past it). **A rule written in machine-evaluable prose is a mechanism someone forgot to finish building, and it is free to finish.**

**⇒ AND THE TIMING BIAS THAT MAKES "REMEMBER TO DO IT" ACTIVELY WRONG, not merely weak.** A step performed from memory at the *tail* of a session fails **precisely when the session ends badly** — crash, interrupt, context exhaustion, a hand-off under load. **That is exactly the population where the handoff surfaces matter most**, because it is the population where the next reader has no other source. So the failures are not randomly distributed across sessions; they are concentrated in the worst ones. **A discipline that holds on every good day and breaks on every bad one is not a control — it is a control's shadow, and it will pass every retrospective audit you run on the good days.**

**⚠️ Scope the new check honestly and write the limit INTO it.** The guard built here compares **vintage, never content** — a surface re-stamped with a fresh `As of:` line over a stale body passes green ([[finding_header_edit_is_the_edit_most_mistaken_for_maintenance]]). It catches the surface **left behind**, not the surface **refreshed badly**. Say which one you mechanized, in the tool's own docstring, so nobody reads its green as the other.

**(e) THE HARD CASE (c) DOES NOT COVER: A RULE THAT CANNOT BE MECHANIZED, REPEATED BY ITS OWN AUTHOR.** *(LABOR, 2026-09-07, n=2 in 10 days on one desk.)* On 8/28 LABOR published *"~7×"* where the arithmetic was `35/4 = 8.75×`, and wrote the corrective **into its own `CLAUDE.md` as a standing rule**: *"any ratio or `N×` gets COMPUTED IN THE ARTIFACT — write the division, not the result."* **Ten days later it told a coordinator a doorbell arrived `~12h` after a delivery; the delivery commit was 17:09:49 and the doorbell ~18:55, so `18:55 − 17:09 = 1h 45m` and `12/1.75 = 6.8×`.** Same shape, no division written, and the rule — self-authored, in the boot-loaded charter, in response to the identical break — did not fire. The coordinator caught it.

**Why (d)'s free-lunch heuristic does not reach this one:** *"write the division"* is **not a comparison anything can evaluate.** There is no surface to diff and no threshold to cross — the defect is a number that was never computed, so there is nothing on disk to check it against. **Some rules genuinely cannot be mechanized, and for those the honest fix is not another check and not more resolve.**

**⇒ WHEN A RULE CANNOT BE MECHANIZED, MECHANIZE THE *SITUATION* INSTEAD — bind it to a recognizable trigger, not to the class of object.** The rule said *figures*, which is why it missed: **both breaks were numbers the author did not experience as figures.** Three features, all present both times, none named by the rule:
1. **The number was an ASIDE, not the claim** — scene-setting inside a sentence whose point was something else. A rule aimed at figures does not fire on figures that feel like phrasing.
2. **It had NO EXTERNAL SOURCE, so recall substituted for measurement.** A market number has a series and a date, so verifying is reflex; **an interval between two things you did yourself feels remembered, not measured** — and recall triggers no verification habit.
3. **It ran in the author's favour** — the first understated their own error, the second overstated a peer's lateness by 6.8×. [[finding_asymmetric_rigor_counterparty_claims]]

**How to apply:** restate the unmechanizable rule as *"when I am about to write a comparative quantity about TIMING or another desk's PERFORMANCE — `N× behind`, `Xh late`, `first`, `still` — write the division beside it from `git log`/`date` before the sentence ships."* **The tell that you are in the failure is that computing it will feel unnecessary, because the number will feel recalled.** ⚠️ And note the reach limit found here: the wrong figure was in a memo's **FILENAME**, consumed into the recipient's `processed/` before the correction — **a body edit cannot reach a path another desk has already logged**, so the correction must be a new artifact.
