**Incident 2026-07-04 (laptop boot).** PROME booted on the laptop and ran the boot repo-state gate — `git status --short` (clean) + `git rev-list --left-right --count HEAD...origin/master` → **`0  0`** → declared boot state ("synced 0/0") and read HANDOFF/SCRATCH/STATUS/HEARTBEAT. Will asked "did you pull all the latest from GitHub?" A `git fetch` then showed origin was **53 commits ahead** — the entire 7/3 + 7/4 desktop-session history, including two later PROME sessions. Everything the first boot declaration was built on was 53 commits stale (wrong OZK date, missing FRED-rotation progress, etc.).

**Why it happens:** `git rev-list HEAD...origin/master` compares against the *local remote-tracking ref* `origin/master`, which is only as fresh as the last `git fetch`. `git status --short` shows a clean *working tree* but says nothing about how far behind origin the clone is. So a clean tree + `0/0` reads as "fully synced" when it can mean "haven't looked at origin since the last machine had it." Under **serial multi-machine** (desktop ⇄ laptop, one box at a time), the machine you *just switched to* is almost always behind — its clone last pulled before the other box did a full day of work + closeout pushes.

**Instance 2 — 2026-08-08, and it generalizes the rule beyond boot.** Mid-session, PROME inspected a *secondary* repo (`~/career-launch`, the career-campaign repo) to answer "can you see this?". `git status -sb` printed `## main...origin/main` with no ahead/behind — read as current — and PROME reported the repo's contents, age and state to Will. It was **16 commits behind**: an entire body of work existed on origin that the clone had never seen. Consequences were not cosmetic — PROME described a finished artifact as an unbuilt scaffold, called an actively-developed repo "dormant for ten weeks," and **wrote a whole document in compliance with an OPSEC rule the operator had RETIRED six weeks earlier**, then proposed as a novel amendment the exact change he had already made. All of it had to be discarded and rewritten.

**The generalization:** the boot gate made this feel like a boot-only discipline. It is not. **Every local clone is a cache, and any clone you read as evidence is a stale witness until you fetch it.** The boot checklist covers the repo you booted in; nothing covers the *other* repos a session wanders into, which is exactly where the assumption goes unexamined. Note the tell was available and ignored — `git status -sb` printing a bare `## main...origin/main` with no `[ahead/behind]` means *"the tracking ref has nothing new to report,"* not *"you are current."*

Same session, same root, different surface: a remote branch was reported to Will as "39 commits that never landed on master" off `git merge-base` ancestry, when a **content** check showed all 27 of its files were already on master and master was newer on every one that differed. Ancestry is not content. A branch whose work landed by squash, re-commit, or a different route is ancestry-unmerged and content-complete — and the reverse is possible too. `[[finding_record_of_an_action_is_not_the_action]]`

**How to apply:** at boot, run `git fetch` (or `git pull --rebase` if the tree is clean/safe) **BEFORE** trusting ahead/behind, declaring "synced," or reading the state files — never trust a `0/0` that hasn't been preceded by a fetch this session. **Extend the same rule to any OTHER repo a session inspects: `git fetch` before reading it, and before reporting anything about its contents, age, or state to the operator.** When a claim about a branch is load-bearing, test it by **content** (`git diff --name-only $(git merge-base <b> main) <b>`, then per-file `git diff --quiet <b> main -- <f>`), never by commit ancestry alone. Highest-risk moment is the first boot after a machine switch. Cheap tell: if `git fetch` prints ref updates (`abc..def master -> origin/master`), your pre-fetch `0/0` was a lie and everything read so far needs a re-read. Relatedly `[[finding_two_machine_partition_clean_merge]]` (the merge is clean, but only *after* you've actually fetched the other box's work).
