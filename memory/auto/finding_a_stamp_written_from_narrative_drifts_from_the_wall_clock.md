**Fact.** On 2026-09-24 three desks stamped artifacts from the narrative clock instead of the wall clock: PROME wrote 22:xx across seven files while `date` read 21:39 (a 40-minute drift over a 40-minute session — the estimate ran at ~2× real time); HENRY's F1-basis packet to TERRY was stamped ~17:0x and was wrong by ~15 minutes (HENRY found it by re-running `date`); SAM's first STATUS pass said ~17:3x and was committed at 16:57. n=3 desks, one day; PROME's own SCRATCH already carried the caution *"take the clock (`NOW:` or `date`) IN THE SAME COMMAND that writes any stamp"* and it did not hold across a long tool-heavy stretch with no user prompt (the `NOW:` hook line arrives only on a user prompt; teammate messages and tool results carry none).

**Why:** a stamp typed from memory of "when I started" plus a felt duration is a claim about the world with no instrument behind it, and the error compounds silently: every later stamp inherits the earlier drift. A wrong stamp is not cosmetic — it re-orders events in the record (a packet stamped after the commit that carries it; a "later leg" that reads as earlier than a peer's delivery) and a reader cannot tell it from a right one.

**How to apply:** never type a clock. In a Bash edit, compute the stamp from `datetime.now()` (or `date`) INSIDE the same command that writes it, and mask minutes to `HH:Mx` only from that value. When a stretch runs on tool results and teammate messages alone (no `NOW:` line), run `date` before the first stamp of every write pass. If a stamp is found wrong before commit, fix it in place and say so in the file; after commit, correct in place with a note — never amend.

**Extended 2026-09-25 (HENRY, n=2 more in one session — two NEW shapes):** ① **the instrument was IN the command and the value was not copied** — a PROME packet header typed "~01:4x" in the same Bash call whose `date` printed 01:10; running `date` is not enough, the stamp must be *interpolated from its output*, never typed beside it. ② **a CLOSEOUT stamp is a forecast** — "session ended ~01:2x" was written into 5 files at 01:15, because a closeout is written BEFORE the session ends; the typed value is the expected finish, not a reading. Stamp the write time (`date` of that write), never the anticipated end. Both caught pre-/post-commit and corrected in place with a note.

**Extended 2026-09-25 (LIQUID, n=1, a THIRD shape: the tool has no clock):** LIQUID's item-3 reply packet to PROME (`PROME/inbox/processed/2026-09-25_from-LIQUID_item3-…md`) was written with the **Write tool** and headed "~01:4x ET"; its commit `53a86c4a8` is 01:11:26. No `date` ran anywhere near it, and none could have: **a file authored through Write/Edit carries a TYPED stamp by construction**, because those tools cannot interpolate a clock. PROME caught it; it was corrected in place at `e700183b2`. Every later LIQUID packet that night was written through a Bash heredoc with `$(date …)` interpolated, and each was right. **How to apply, added:** a stamp goes into a file only through a command that reads the clock. When a file is authored with Write, leave the stamp out and patch it in with a `date`-interpolating `sed` before commit. ⚠️ "~01:4x" also appears in 9/25 packet headers from BOND and HENRY (`grep -l '01:4x' PROME/inbox/processed/`); those were NOT checked against their commits and are not counted here.
