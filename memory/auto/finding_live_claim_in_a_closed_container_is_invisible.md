Sweeps for open work — boot scans, closeout checks, "what do we still owe?" passes — key on the **container's** status, not on each claim inside it. So **a live claim parked in a container marked DONE is invisible by construction.** It is not hidden; it is in plain sight, in a file that is read constantly, and it still gets skipped, because the thing being read is the header.

**NEXUS, 2026-08-03.** `CONFIRMED.md` is a trophy case — every row asserts *this happened*, and rows carry a confidence like 99%. Row **C-05** described three legs, two fired and one **forward**: *"Wave 1 exhaustion fired. Wave 2 peak Apr 26. CA/NY Aug."*

That third leg sat unresolved from **March to August**. It survived:
- every boot's open-items scan (the row's status is *confirmed*),
- two separate audit passes that flagged it in prose and still did not resolve it,
- and its own arrival **in-window**, which changed nothing because nothing was watching.

When it was finally checked, the leg turned out to be **unresolvable from birth** — it named no instrument, no threshold and no magnitude, so **no print could ever have fired it in either direction** (`[[finding_resolvability_defect_is_status_not_confidence]]` — that is a STATUS change to STUCK, not a confidence cut). **Two independent defects, five months, both hidden by the same thing: the row's header said confirmed.**

**The rule.** A container whose status means *finished* must contain only finished things.
- **Fired legs stay; forward legs move out** — to the predictions ledger / open-items tracker — with an instrument, a threshold and a date. The closed row **links** to the open item rather than holding it.
- **When a legacy row already mixes both**, do not rely on prose to flag it. Give the forward leg **its own status cell** (`STUCK`, `RE-SPEC'd`, a resolve date) so that a machine or a skim keys on the leg, not the row, and **state explicitly which legs the headline number applies to.**

**Generalizes past state files.** Same shape wherever status is inherited downward: an open question inside a closed ticket · a TODO inside a merged PR description · an unverified figure inside a "verified" summary · a pending item in a section headed RESOLVED · a caveat inside an artifact stamped APPROVED. In each case the audit reads the container.

**The tell:** you are writing a sentence in the future or conditional tense — *"expected," "should hit," "by August," "if X then"* — into an artifact whose whole purpose is to record the past. If the tense of the claim disagrees with the tense of the container, the claim is in the wrong file.

**n+1 (PROME, 2026-08-16) — the CONSUMED PACKET is a closed container too, and filing it IS the close.** DAEDALUS's 8/7 consolidated packet carried a fired retirement trigger with a Will-gated tail: consumer_check v3 had shipped (`98aca1558`), so root CLAUDE.md §1c's interim caveat — whose own text said *"retires when unit-aware matching ships"* — was due for retirement, replacement text proposed in the packet. PROME consumed the packet, executed its other items, filed it to `processed/` — and the Will-gated tail died with the container. **Nine days later PROME re-derived the item backwards as "nothing has shipped"** (reading the still-standing caveat as evidence of a missing fix — the stale surface indicted the shipped code). DAEDALUS caught it only because the resurfaced wrong premise crossed its desk. **The rule's packet form: at consumption, any tail you cannot execute now (Will-gated, blocked, deferred) gets a row on a surface that RE-PRINTS until dispositioned — WILL_QUEUE for Will-gated, DOCKET for dated (its DEFERRAL RULE already mandates this for decisions; packet tails are the same class) — BEFORE the packet moves to processed/. Filing to processed/ is a status change on everything inside it.** Corollary tell: if you find yourself concluding "X never shipped" from a surface that X was supposed to update, check the commit log for X before publishing the negative — a standing caveat is evidence its RETIREMENT didn't ship, not that the fix didn't.

**n+2 (PROME, 2026-08-16 S4 — the same evening n+1 shipped, its first live test, and it missed) — the rule's trigger is the TAIL'S BIRTH, not the packet lifecycle.** Hours after n+1 was written, PROME drafted a Will-gated proposal in-session (root active-list trim, header explicitly "for Will's ruling") and registered no queue row. The n+1 rule never fired because there was no packet to file — the tail was born outside any container the rule watched. DAEDALUS's sweep caught it the same night; it was mooted only because Will happened to rule within ~90 minutes, which is luck, not a mechanism. **General form: a Will-gated (or blocked/deferred) tail gets a row on a surface that RE-PRINTS until dispositioned AT THE TAIL'S CREATION, whatever surface it is born on** — packet consumption, in-session draft, verbal ask, commit message. n+1's filing clause is one instance of this rule, not the rule.

**n+3 (PROME, 2026-08-21 late) — the LIVE SESSION TRANSCRIPT is the container, and inbound relayed content is the claim.** Will pasted RAV's 12-item operating-improvements feedback (a Telegram relay) into PROME's session and asked for thoughts. PROME analyzed and answered — disposition delivered, thread apparently complete — while the feedback itself existed **nowhere on disk**. Same night, Will directed DAEDALUS to review "the updates RAV supplied": DAEDALUS swept every RAV channel it knew (branches, QC ledger, inbox, PRs, untracked files) and correctly found **nothing newer than 8/16** — a clean scan of every durable surface, while the artifact sat in a container none of them could see. Caught only because DAEDALUS asked the live session directly; had the session closed first, the feedback would have survived only as HANDOFF narrative — a paraphrase, not the artifact. **The rule's relay form: operator-relayed content (reviewer feedback, pasted external text, a forwarded message) gets filed to disk VERBATIM, with provenance, the same session it arrives — BEFORE disposition, not after.** The disposition references the file; the file never depends on the session. Tell: you are analyzing quoted text that has no path — if you cannot name the file a peer would find it in, file it first.

**n+4 (LABOR, 2026-08-23) — THE RULE IS BIDIRECTIONAL, and the reverse direction bills the OPERATOR.** Every instance above is a *live* claim in a *done* container. The mirror is a **discharged item left inside a container headed LIVE**, and it fails differently: it does not rot quietly, it **manufactures work**.

LABOR's `BUILD_DEBT.md` had a section headed `## Live debt` holding **9 discharged rows**, each one's closure correctly recorded — in the **last column of rows hundreds of characters wide**. Asked by the operator for next steps, LABOR read the problem statements in column 2, never reached the resolutions in column 6, and **recommended BD-15 and BD-17 to Will as live gaps.** Both had been closed **16 days earlier**, and closed substantively (a threshold re-specced onto EPOP and base-rated 1990-2026; another killed on a measured +0.0pp separation). **The register was correct. The skim was the instrument that failed, and the heading is what made the skim wrong.**

Aggravating detail worth keeping, because it shows how little authority "I know about this failure" carries: **LABOR had fixed three stale inventories in its own boot-loaded docs earlier in the same session** — a stale prediction flag-list, a "live cards: none" line, a wrong card count — and then committed the identical class of error against its own register **within the hour**.

**The symmetric rule:** *a container whose status means finished must contain only finished things* — **and a container whose status means LIVE must not silently hold finished ones.** Where rows are too content-rich to move (the resolution text is often the most valuable thing in the register), **do not fix it by moving them; fix it by making status visible at the START of the row** — a ✅ on the ID, plus an honest heading that says the table holds both, plus a **re-derivable** count (`grep -c '^| ✅' FILE`) rather than a hardcoded one, since a hardcoded count is the same defect one level up.

**The tell, and it is cheap:** if an item's STATUS lives further right than a reader's eye travels, the **heading** is the status for all practical purposes. Ask of any register: *could someone skim the left column and get the status wrong?* If yes, the status is in the wrong column, whatever the row actually says.
