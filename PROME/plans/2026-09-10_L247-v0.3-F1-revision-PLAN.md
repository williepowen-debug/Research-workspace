## B. The design decision (and the declared departure from RED's rec)
RED's rec: (vi′) pin the ruled `outcome_map` bytes as `outcome_map_sha256` (the mapping check = "is this the map a human ruled?"), plus (vii) every label carries ≥1 branch, plus masses inside the ruled bytes. No parser.

v0.3 takes RED's (vii) and the ruled-bytes pin, but makes the **mapping check itself a containment test against the accepted event**, not a self-pin:
- The accepted `QuestionRegistered` event is immutable and is IN the render input; the ruling record is not. §2 already names the event's `resolution_rule` as the authority for labels and mapping. A pin of the entry's own bytes authenticates what was ruled; only the event can authenticate that the map is the rule's.
- The rule states the mapping in a fixed token form: `(a) -> YES, (b) -> NO, (c) -> AMBIGUOUS, (d) -> AMBIGUOUS.` The renderer FORMS each claimed pair string from `outcome_map` and asks whether the immutable string CONTAINS it. That is `substring in string` on a machine-formed literal — no extraction, no regex, no interpretation. Nothing is read INTO the prose; the prose is asked whether it contains what the registry claims.
- Fail direction: a rule that does not state every pair in that form makes the entry **unregistrable under the bridge** (refuse). The question waits for §1b. The renderer never guesses.
