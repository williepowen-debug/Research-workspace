## 3. Scoring rule — gate item 3
For a vectored row, `brier_score` = **½ · Σ_{k ∈ V} (p_k − 1[k = realized])²** — the half-normalized multiclass Brier, range [0, 1].

**Why this one.** For K = 2 with p_NO = 1 − p_YES it reduces EXACTLY to (p_YES − o)², which is what the existing binary column computes today — so one column, one convention, and binary rows are unchanged by construction rather than by promise. The unnormalized form (Σ, range [0, 2]) carries the same information on a different scale and would make rows in one column incomparable. "Binary on the realized label" ((1 − p_realized)²) is **REJECTED**: it discards the distribution over the non-realized labels — 0.45/0.20/0.35 and 0.45/0.55/0.00 would score identically, which is precisely the information the vocabulary was admitted to keep.

**Worked example — MIDAS-06, realized YES:** ½ · [(0.45 − 1)² + (0.20 − 0)² + (0.35 − 0)²] = ½ · [0.3025 + 0.0400 + 0.1225] = ½ · 0.4650 = **0.2325**. The amendment's three candidates: 0.3025 (binary-on-realized — rejected) · 0.465 (unnormalized — same information, wrong scale for the column) · **0.2325 — adopted**. Decimal arithmetic throughout; output through the existing `format(….normalize(), "f")`.

**Disclosure.** `CALIBRATION.tsv` gains ONE appended column `score_basis` ∈ {`BINARY`, `MULTICLASS_HALF_NORMALIZED:<K>`}. Every existing row reads `BINARY`; the vectored row reads `MULTICLASS_HALF_NORMALIZED:3` — a reader who recomputes (1 − 0.45)² = 0.3025 sees at once why the cell says 0.2325. The vocabulary and masses are recoverable from the registry (in the digest) and from the question's `resolution_rule`; they are not repeated per row. **`score_basis` is also the scorability discriminator (F7): a `BINARY` row keeps today's path where a realized AMBIGUOUS renders UNSCORED (`render.py` 180–192); a `MULTICLASS_HALF_NORMALIZED:<K>` row scores AMBIGUOUS as a label like any other — two realized-AMBIGUOUS rows can therefore differ in scoring, and the column says why.**

## 4. Validation — gate item 4
Two failure classes, deliberately different. **Registry/entry defects (structural, or a contradiction between the registry and the accepted records) ⇒ `ValueError` ⇒ the render REFUSES** — a malformed or contradictory registry never degrades to "no vectors", because the failure it guards is a score that looks right. **Row states ⇒ the row renders with an `exclusion_reason` token and no score** — a legitimate state of one row must not withhold the whole view.
**Registry:** `schema_version` / `registry_id` exact; `entries` is an array; one entry per `question_id`; required keys present and non-empty strings where strings are required.
**Entry:** `outcome_vocabulary` is an ordered list, length ≥ 3, each label ∈ `OUTCOME_VALUES` − {`ANNULLED`} (= {YES, NO, AMBIGUOUS} in v1), no duplicates · `probability_vector` keys == set(`outcome_vocabulary`) exactly — no missing label, no extra key · each value a Decimal string in [0, 1] · **Σ == 1 exactly in Decimal, no tolerance** (the author rounds the letter's "~" masses to a declared precision and says so in `mapping_note`; MIDAS-06 sums exactly at two decimals) · `forecast_version` ≥ 1 · `outcome_map` rows carry exactly `branch` · `outcome` · `mass` · `ruled_bytes_sha256` present (§4 (viii); absence refuses).
**Cross-checks at render, against replay state — REFUSE class:** (i) `forecast_event_id` exists in the replayed input and is the submission/amendment event of that `forecast_id` at that `forecast_version` — else `VECTOR_EVENT_UNKNOWN` (refuse) · (ii) `probability_vector["YES"]` == that version's scalar `probability` in Decimal — the declaration may ADD masses, never contradict the accepted event — else `VECTOR_CONTRADICTS_EVENT` (refuse) · (iii) no entry for the same `question_id` in `projection-exclusions.json` — both present ⇒ `PROJECTION_METADATA_CONFLICT` (refuse); the MIDAS-06 exclusion entry is REMOVED in the same ruled change that adds its vector (one registry pair cannot both exclude and score a row) · (iv) the question's `forecast_family` is `BINARY_PROBABILITY` — trivially true in v1 (the schema's `const`), recorded so the bridge is retired when §1b lands; no token, cannot fail today (F8: retirement carrier = the §1b DOCKET row, session-keyed `next-KERNEL-spec-pass`) · **(v) `outcome_map` is present, its `branch` values are unique, for each label k: `probability_vector[k]` == the Decimal SUM of `outcome_map` masses whose `outcome` is k, and the Σ of all `outcome_map` masses == 1 — else `VECTOR_MAP_MISMATCH` (refuse) (F1). That the entry's branch set is the LETTER's — exhaustive, nothing invented — is the reviewer's check at ruling, not a render check: the letter is not a render input (leg 1 restated v0.3; the v0.2 wording asked the renderer for a set it cannot see)** · **(vi) MAPPING — the branch→outcome assignment in `outcome_map` is the one the accepted question event `EVT-…006a` states.** For every `outcome_map` row, iterated in `branch` order (the order (viii) serializes), the renderer forms `PAIR_FORM = "(" + branch + ") -> " + outcome` (ASCII, single spaces — the token form the accepted rule uses) and requires (α) that literal to occur in the replayed `resolution_rule`, and (β) for every OTHER label k in `OUTCOME_VALUES − {ANNULLED}`, iterated in sorted label order (the Kernel's set, not the entry's own `outcome_vocabulary`; `core.py` holds it as a set, so the order is imposed here), the literal `"(" + branch + ") -> " + k` NOT to occur — else `VECTOR_RULE_MISMATCH` (refuse; the reason text names the pair). This is exact-string containment of a machine-formed literal in an immutable string: no extraction, no regex, nothing read INTO the prose — the rule's meaning stays where §2 puts it, with the reviewer at ruling time. `resolution_rule_sha256` is KEPT as the document-identity pin (a different question — is this the rule the ruling read? — same token, reason text names the leg). **Premise, stated as a registrability condition:** containment treats every PAIR_FORM occurrence in `resolution_rule` as an assertion of the mapping; a rule in which a PAIR_FORM literal appears in any other role (negated, quoted, hypothetical) is NOT PAIR_FORM-stated, and the reviewer confirms at ruling that the rule's only PAIR_FORM occurrences are its mapping sentence (MIDAS-06: one sentence, four pairs, the DO-NOT clauses live in `ambiguity_rule`, which (vi) does not read — VERIFIED 2026-09-10). β is prefix-safe only because no v1 label is a prefix of another (YES · NO · AMBIGUOUS); a future vocabulary keeps that property or β is re-specified. **Legacy questions whose accepted rule does not state the mapping in PAIR_FORM: no entry is registrable** — the question stays EXCLUDED under `projection-exclusions.json` (`OUTCOME_VOCABULARY_MISMATCH`, the state MIDAS-06 held before this spec); §1b cannot reach an already-accepted record, so it is not the carrier.
