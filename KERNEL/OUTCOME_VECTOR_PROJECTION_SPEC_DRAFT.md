## 0. The problem, once
The accepted records carry no structured three-outcome vector: `question.schema.json` permits only `forecast_family: BINARY_PROBABILITY`; `forecast.schema.json` stores one scalar `probability`; `core.py` rejects every other family (`FAMILY_NOT_ENABLED`); `render.py` computes a binary Brier from the scalar. MIDAS-06's accepted forecast carries `probability: 0.45` only; the NO 0.20 / AMBIGUOUS 0.35 masses live in prose (`decision_consequence`; the native companion). Reading them from prose or from a mutable file would break the event-derived model — and "scores on the declared mass" admits three numbers (0.3025 · 0.465 · 0.2325). This spec answers the amendment's five items in order.

## 3. Scoring rule — gate item 3
For a vectored row, `brier_score` = **½ · Σ_{k ∈ V} (p_k − 1[k = realized])²** — the half-normalized multiclass Brier, range [0, 1].

**Why this one.** For K = 2 with p_NO = 1 − p_YES it reduces EXACTLY to (p_YES − o)², which is what the existing binary column computes today — so one column, one convention, and binary rows are unchanged by construction rather than by promise. The unnormalized form (Σ, range [0, 2]) carries the same information on a different scale and would make rows in one column incomparable. "Binary on the realized label" ((1 − p_realized)²) is **REJECTED**: it discards the distribution over the non-realized labels — 0.45/0.20/0.35 and 0.45/0.55/0.00 would score identically, which is precisely the information the vocabulary was admitted to keep.

**Worked example — MIDAS-06, realized YES:** ½ · [(0.45 − 1)² + (0.20 − 0)² + (0.35 − 0)²] = ½ · [0.3025 + 0.0400 + 0.1225] = ½ · 0.4650 = **0.2325**. The amendment's three candidates: 0.3025 (binary-on-realized — rejected) · 0.465 (unnormalized — same information, wrong scale for the column) · **0.2325 — adopted**. Decimal arithmetic throughout; output through the existing `format(….normalize(), "f")`.

**Disclosure.** `CALIBRATION.tsv` gains ONE appended column `score_basis` ∈ {`BINARY`, `MULTICLASS_HALF_NORMALIZED:<K>`}. Every existing row reads `BINARY`; the vectored row reads `MULTICLASS_HALF_NORMALIZED:3` — a reader who recomputes (1 − 0.45)² = 0.3025 sees at once why the cell says 0.2325. The vocabulary and masses are recoverable from the registry (in the digest) and from the question's `resolution_rule`; they are not repeated per row. **`score_basis` is also the scorability discriminator (F7): a `BINARY` row keeps today's path where a realized AMBIGUOUS renders UNSCORED (`render.py` 180–192); a `MULTICLASS_HALF_NORMALIZED:<K>` row scores AMBIGUOUS as a label like any other — two realized-AMBIGUOUS rows can therefore differ in scoring, and the column says why.**

## 4. Validation — gate item 4
Two failure classes, deliberately different. **Registry/entry defects (structural, or a contradiction between the registry and the accepted records) ⇒ `ValueError` ⇒ the render REFUSES** — a malformed or contradictory registry never degrades to "no vectors", because the failure it guards is a score that looks right. **Row states ⇒ the row renders with an `exclusion_reason` token and no score** — a legitimate state of one row must not withhold the whole view.
**Registry:** `schema_version` / `registry_id` exact; `entries` is an array; one entry per `question_id`; required keys present and non-empty strings where strings are required.
**Entry:** `outcome_vocabulary` is an ordered list, length ≥ 3, each label ∈ `OUTCOME_VALUES` − {`ANNULLED`} (= {YES, NO, AMBIGUOUS} in v1), no duplicates · `probability_vector` keys == set(`outcome_vocabulary`) exactly — no missing label, no extra key · each value a Decimal string in [0, 1] · **Σ == 1 exactly in Decimal, no tolerance** (the author rounds the letter's "~" masses to a declared precision and says so in `mapping_note`; MIDAS-06 sums exactly at two decimals) · `forecast_version` ≥ 1.
**Cross-checks at render, against replay state — REFUSE class:** (i) `forecast_event_id` exists in the replayed input and is the submission/amendment event of that `forecast_id` at that `forecast_version` — else `VECTOR_EVENT_UNKNOWN` (refuse) · (ii) `probability_vector["YES"]` == that version's scalar `probability` in Decimal — the declaration may ADD masses, never contradict the accepted event — else `VECTOR_CONTRADICTS_EVENT` (refuse) · (iii) no entry for the same `question_id` in `projection-exclusions.json` — both present ⇒ `PROJECTION_METADATA_CONFLICT` (refuse); the MIDAS-06 exclusion entry is REMOVED in the same ruled change that adds its vector (one registry pair cannot both exclude and score a row) · (iv) the question's `forecast_family` is `BINARY_PROBABILITY` — trivially true in v1 (the schema's `const`), recorded so the bridge is retired when §1b lands; no token, cannot fail today (F8: retirement carrier = the §1b DOCKET row, session-keyed `next-KERNEL-spec-pass`) · **(v) `outcome_map` is present, every branch letter of the pinned letter appears exactly once, and for each label k: `probability_vector[k]` == the Decimal SUM of `outcome_map` masses whose `outcome` is k — else `VECTOR_MAP_MISMATCH` (refuse) (F1)** · **(vi) the branch→outcome assignment in `outcome_map` agrees with the accepted question event's `resolution_rule`: v1 satisfies this by an exact-string pin — `resolution_rule_sha256` == sha256 of `EVT-…006a`'s `resolution_rule` as replayed, no prose parsing — else `VECTOR_RULE_MISMATCH` (refuse) (F1). Why (ii) alone is not enough: the scalar IS P(a), fixed by the immutable event; without (v)+(vi) a (c)→NO or a (b)↔(d) swap ({0.45, 0.15, 0.40}, both 0.20 masses interchangeable) passes every check and renders 0.2425 for 0.2325.** **Row states — EXCLUSION class (the row renders, unscored):** the vocabulary in v1 is exactly {YES, NO, AMBIGUOUS} (length ≥ 3 from a three-label set), so a realized YES/NO/AMBIGUOUS is always covered — `ANNULLED` keeps today's `OUTCOME_ANNULLED` path · `_calibration` renders ONE ROW PER FORECAST VERSION with no ACTIVE filter (render.py `for version in forecast["versions"]`), so a vectored forecast's OTHER versions — every version the entry does not name — render `VECTOR_VERSION_UNDECLARED`, unscored (neither formula applies to them; MIDAS-06 has one version, so no row is affected today) · **before finality** every row renders `QUESTION_NOT_FINAL` as today; vectors never score an open question.
